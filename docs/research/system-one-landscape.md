# Research: System One backend landscape — which should a personal decision layer default to?

Wayfinder ticket: [bearmoth/dotfiles#45](https://github.com/bearmoth/dotfiles/issues/45) (child of map #44). Researched 2026-10-01.

## Question

Which System One backend (Jev/TypeSafe, AnyJev, Laya) should a personal decision layer — routing skill/model/effort choice for coding agents, destructive-command checks — default to, and on what current evidence?

## Verdict

Default to **Jev (`jev-1.13.0`, pinned, via the hosted API)**: the only backend with strong zero-shot quality on small-option routing tasks (0.91 acc on a 4-way pilot) at near-zero personal cost. **AnyJev**: no shipped Jev-compatible server, no verified Apple Silicon/Fedora-CPU path — skip. **Laya**: self-hosts on Apple Silicon (confirmed) at zero cost, but near-chance zero-shot on its own routing benchmark and a documented `noul` bug — not ready without fine-tuning. The closest independent study to "destructive-command checks" (111 cases, Jev vs Claude Opus 5) found them statistically tied (100/111 vs 102/111); each model's one unsafe allow traced to a *different* deterministic-layer gap (§4), not a shared model flaw — fix the policy layer, not the model choice. Circuit breaker (§1): `429`→hold `retry_after_ms`/`Retry-After`; `529`/5xx→backoff; everything else, `402` included→stop and alert.

## 1. Jev / TypeSafe AI

**Pricing (verbatim from [docs.typesafe.ai/models](https://docs.typesafe.ai/models.md), fetched 2026-10-01):** "$42 / $0.042" per billion/million input tokens; output tokens are free.

**Rate limits — verbatim, as-of 2026-10-01:** "100K tokens per second / 40 requests per second" (= 2,400 req/min). The docs carry an explicit live warning: *"Rate limits are adjusting dynamically. We are serving a very large volume of demand, and the limits above can change without notice... as upcoming large GPU deals land and we let in more users."* Against the Sep-2026 GA baseline (250K tok/s, 1,200 req/min), tokens/sec roughly halved while requests/sec roughly doubled — not a uniform tightening, and TypeSafe itself frames the numbers as actively moving, not a stable ceiling. Both figures are far above personal-use volume regardless. Higher limits: enterprise plans, sales@typesafe.ai.

**Budgets:** 64k tokens/request total (state + all questions); 32k tokens for state + the single longest question. Text-only input (string/JSON/array) — no image/audio/video.

**Model IDs / pinning / deprecation:** `jev-1.13.0` is the only versioned model published today; `jev-latest` and `jev-preview` both alias to it (`jev-preview` has no actual preview build ahead of latest right now). Docs recommend pinning the versioned ID once thresholds are tuned, since aliases move between releases and silently shift calibration. **No documented deprecation-notice period for a versioned ID was found** in any fetched page — a gap, not a confirmed absence; ask TypeSafe directly before depending on long-lived pins. The dedicated "jev-1.13 jaggedness" page documents nine known failure modes (can't count, can't do date arithmetic, degrades under indirection/irrelevant detail, not adversarial-robust, no structural-consistency guarantee across questions, never generates text) — load-bearing for anything gating destructive commands.

**Data retention / training / DPA (quotes below verified against the DPA's raw HTML directly, not just a fetch-tool summary):** The Data Processing Addendum ([typesafe.ai/legal/data-processing](https://typesafe.ai/legal/data-processing)) ties retention to operational necessity rather than a fixed period: *"Customer Personal Data will be retained for as long as necessary taking into account the purpose of the Processing, and in compliance with applicable laws, including laws on the statute of limitations."* §3 (Subprocessors): new subprocessors require advance notice, and *"Customer may object to the appointment of such new Subprocessor within 15 days of the date of such notice... on reasonable privacy or security grounds."* Breach notification: *"Typesafe will notify Customer without undue delay and in any case within 72 hours after becoming aware of any accidental or unauthorized access to, or disclosure or use of, Customer Personal Data."* **The DPA itself contains no SLA or uptime commitment.** The actual subprocessor list lives at `trust.typesafe.ai/subprocessors` — a Vanta-powered trust center that renders via JavaScript; I could not retrieve its contents with a plain fetch, so the subprocessor list itself is unverified (see Open Questions). The Privacy Policy (last updated 2025-11-19, [typesafe.ai/legal/privacy-policy](https://typesafe.ai/legal/privacy-policy)) separately commits *"We will not train or fine tune any artificial intelligence or machine learning models on your prompts or other Input."* Zero data retention (ZDR) is offered to enterprise customers via sales@typesafe.ai. For a workplace (`easygo`) vendor check, this is workable but not maximally strong: no fixed retention ceiling, no SLA, ZDR gated behind a sales conversation.

**Status / SLA:** [status.typesafe.ai](https://status.typesafe.ai/) (Better Stack-powered). As of 2026-10-01 07:11 UTC: API 99.829% uptime (90-day trailing), console 99.976%. ~10 incidents in the preceding 30 days, mostly 2–18-minute "Downtime" or "Elevated API latency" entries. No SLA found on the status page either (consistent with the DPA above).

**Wire-format for quota/rate-limit/downtime — now confirmed against first-party SDK source, not just docs:**
- `docs.typesafe.ai/api.md`'s error table documents exactly four statuses for the decision endpoint: `401` (bad/missing key), `422` (validation failure), `429` (rate limit — "back off and retry after a short delay"), `529` (overloaded — same advice). Both the JS SDK (`src/errors.ts`, `APIError.fromResponse`) and the Python SDK (`_core/errors.py`, `STATUS_ERROR_TYPES`) additionally special-case `400`, `403`, `404` and any `>=500` → a generic `InternalServerError`/`TypeSafeInternalServerError`. **`402` is absent from both maps.** A `402` response would construct the generic base class (`APIError` in JS, `TypeSafeAPIError` in Python, via the `else` branch) — no subclass, no special handling, and it is *not* in either SDK's default retry set (`408`/`429`/`500–599` only, confirmed in `src/retry.ts` / `_core/retry.py`), so a default-configured SDK call would correctly surface it as an error rather than silently retrying it.
- `429`'s `retry_after_ms` is confirmed, by reading the Python SDK source directly, to come from parsing **both** a `retry-after-ms` header **and** the standard `Retry-After` header (handling both delta-seconds and HTTP-date formats) — so "honors a standard `Retry-After` header" is now a confirmed fact, not an inference. No rate-limit-remaining or absolute-reset-timestamp header is documented or present in the parsed set. The default retry set itself is also now confirmed directly from `_core/retry.py`: `http_statuses: set[int] = {408, 429, *range(500, 600)}` — exactly the 408/429/5xx set stated above, read from source rather than inferred from docs.
- **Credit/quota exhaustion has no documented or SDK-level representation at all.** This is itself informative: if TypeSafe ever returns a payment-required-style response, there is currently no first-party code path that recognizes it as anything other than a generic, non-retried error. Separately, a Sep-29-2026 [Vercel AI Gateway community thread](https://community.vercel.com/t/ai-gateway-typesafe-ai-jev-returns-free-tier-429-despite-paid-credits/49935) reports a user whose paid AI Gateway credits still returned **`429 rate_limit_exceeded`** ("No access to this model at this time", `providerAttemptCount: 0` — the request never reached TypeSafe) — i.e., through at least one third-party gateway, a credit/tier problem can present with the *same status code* as ordinary rate limiting, indistinguishable to the caller. That specific failure is gateway-side (Vercel's own tier gating), not confirmed TypeSafe-direct behavior, but it's a reason not to assume "429 always means safe-to-retry" the moment a gateway is in the path.
- **Practical implication for the circuit breaker:** calling TypeSafe directly, you can cleanly separate rate-limit (`429`, hold for `retry_after_ms`/`Retry-After`) from downtime (`529`/5xx, open circuit, exponential backoff per the docs' own advice) from validation/auth errors (`422`/`401`, fix the request, don't retry). For `402` or any other unlisted status — and for any `429` arriving through a gateway rather than TypeSafe directly — treat it as "stop and alert a human," since nothing in the first-party stack claims to handle it as transient.

## 2. AnyJev

Repo: [nokia-applied-research/AnyJev](https://github.com/nokia-applied-research/AnyJev), Apache-2.0, v0.2.0 (2026-09-28).

**Jev-compatible HTTP server: not shipped.** Listed, unchecked, under `ROADMAP.md`'s "Next" section as of today: *"Jev-compatible HTTP server... `POST /v1/decisions`... Done: the suite passes... and a chat-completions body gets a 400."* What **is** shipped is vLLM serving of the internal pooling head (`--task embed` + a custom pooler) — not a drop-in Jev-API-shaped endpoint.

**Supported backends:** `transformers` (HFBackend) and `vLLM` (VLLMBackend), plus a `FakeBackend` for CPU-only testing with no model. SGLang, llama.cpp, MLX, and Ollama backends are explicitly listed as **"help wanted," not implemented**.

**Running locally — Apple Silicon Mac:** no mention of Apple Silicon, Metal, or MPS anywhere in the README, roadmap, or changelog. All published latency/accuracy numbers were measured on an H100 NVL (CUDA). vLLM is CUDA-first with no mainline Metal backend, so the vLLM path (needed for the useful L2 closed-form-head mode) is **not available** on a Mac. `transformers` could in principle run on MPS/CPU, but AnyJev has never published a number for it.

**Running locally — Fedora x86-64:** works today with an NVIDIA GPU (vLLM/CUDA); CPU-only falls back to `transformers`, again unpublished.

**Latency (their own measured numbers, `docs/results_latency.md`, one H100 NVL, bf16) — K=4, the 3–6-option routing shape:**

| Backend | state tokens | batch raw | batch L0 (4 shifts) | single raw | single L0 |
|---|---|---:|---:|---:|---:|
| transformers, Qwen3-8B | 110 | 10.7ms | 42.8ms (4.0×) | 48.5ms | 54.6ms (1.1×) |
| vLLM, Qwen2.5-7B, prefix cache on | 121 | 9.2ms | 28.2ms (3.1×) | 33.3ms | 61.8ms (1.9×) |

These are H100 numbers; there is no published Apple Silicon or CPU equivalent for AnyJev itself.

**Memory (computed from parameter count at bf16, not measured):** Qwen3-1.7B ≈ 3.4GB, 4B ≈ 8GB, 8B ≈ 16GB, 32B ≈ 64GB, 30B-A3B ≈ 60GB resident (MoE — only ~3B active per token, but the full weight set must still be loaded). An 8B+ model is the practical floor for competitive L2 accuracy, meaning ~16GB+ of VRAM/unified memory just to hold weights, before KV cache.

**Model size / accuracy tradeoff (LocalLLaMA/typed-decisions bench, 300 labels/question, 2,000 held-out decisions):** zero-label `L0` alone is mediocre (Qwen3-8B: 0.647); competitive numbers require **L2** (a closed-form head fit on 100–300 labeled examples *per question*): Qwen3-1.7B 0.730 @ 64% depth, Qwen3-4B 0.786 @ 67%, Qwen3-8B 0.771 @ 67%, Qwen3-30B-A3B 0.799 @ 83%, Qwen3-32B 0.798 @ 81% — beating TypeSafe's own published Jev number (0.727) on the same set, but only *after* a labeling investment a personal decision layer doesn't have on day one.

**Verdict for this use case:** not viable today — no compatible server, no verified Apple Silicon or Fedora-CPU path, good numbers gated on labels.

## 3. Laya

[huggingface.co/convaiinnovations/laya](https://huggingface.co/convaiinnovations/laya), Apache-2.0. **No new checkpoints since the Sep-2026 baseline** — still exactly three: `laya` (421M, ModernBERT-large, English), `laya-multilingual` (322M, mmBERT-base), `laya-typed-decisions` (421M, fine-tuned). Runtime bumped to **0.3.20** (long-document support, OOM-fallback fixes, `laya-serve` fixes).

**Zero-shot vs fine-tuned, on Laya's own typed-decisions benchmark (2,000 decisions, 4 workflows):** base checkpoints score **0.362/0.352 against a 0.318 random baseline and a 0.461 majority-class baseline — near chance, worse than guessing the majority label.** The fine-tuned `laya-typed-decisions` checkpoint reaches **0.766 — above Jev's published 0.727, and above the 0.735 "teacher self-agreement ceiling"** (the rate at which a fresh sample from the labeling LLM agrees with its own prior labels — the practical ceiling for anything graded against that teacher). The project's own conclusion, verbatim: *"Treat Laya as a fast base to specialise, not as a zero-shot decision engine."*

**A second, independent data point, read correctly this time (composite scores blend in Speed and Cost, which isn't what "zero-shot quality" means — use the Intelligence axis and per-tier accuracy instead).** [JevBench](https://github.com/fstandhartinger/jevbench) (not TypeSafe- or Convai-affiliated) ran the stock `laya` (421M) checkpoint zero-shot on its own 534-decision suite (v1.2.2, their CPU, 4 threads), ranking **#33 of 48 ranked rows in that revision — the lower third, not mid-pack.** Intelligence axis: 45.8 (vs Jev 1.13.0's 85.7 in the same table). Per-tier accuracy: **94.4% / 72.9% / 69.2% / 34.1%** (easy/standard/judge/hard) — the hard tier, which uses longer states, is where it falls apart, and JevBench's own footnote names the reason: *"Its budget is 512 tokens per question, so long hard-tier states are cut by the package itself."* **Net read: Laya's zero-shot quality is weak everywhere independently measured — near-chance on its own vendor's typed-decisions benchmark, lower-third on JevBench's broader suite — and the state-budget ceiling is an independently-confirmed, compounding problem on top of that** (a coding-agent routing decision — recent turns + a diff + a shell command — easily exceeds 512–1,024 tokens before you've even stated the question; Jev's 32k budget doesn't).

**A specific, relevant bug:** per the project's own README, `noul` questions render their two options as `false:`/`true:` by default, and **on the English checkpoint this label pair can dominate the answer, returning a confident "no" for clearly positive input** (README-tracked as issue #156; I did not check live issue state, so treat "open" as per-README, not independently confirmed). A `noul`-shaped "is this command destructive?" check is exactly the kind of question this bug would hit — validate this specific failure mode, or use the documented workaround (override the model-facing label pair, keep the result interpreted as P(true)), before using Laya `noul` for a destructive-command gate. `score` (ordinal) is separately documented as "the weakest primitive" (SST-5 0.372) — relevant to effort-level routing specifically.

**Apple Silicon — genuinely supported, with independent confirmation.** The project's own quickstart cites ~1.7s for a 4,000-token document "on an Apple GPU"; a community MLX port, [laya-apple](https://github.com/tc3oliver/laya-apple) (also packaged as `laya-mlx`), exists. Independent third-party evidence: [ReallyArtificial/stuntdouble](https://github.com/ReallyArtificial/stuntdouble)'s first launch report (2026-09-22) ran `laya-mlx` 421M successfully on a **MacBook Pro M3 Pro, 18GB unified memory**, alongside [Kev](https://github.com/jaredpalmer/kev)-0.8B via MPS — both ran fine, but **Kev-4B did not fit**: it "swapped the machine to a standstill during load" on one attempt, and on a retry the first real request hung 180s while swap climbed to 13GB. (Jev itself was not run in that report — no API key was available on that machine — so it's Kev-vs-Laya locally, not a Jev-vs-local comparison; the author flags that comparison as still outstanding in their own issue tracker.) Net: **Laya is the one backend in this research with independently-confirmed, working Apple Silicon numbers**; a Jev-compatible local alternative (Kev) also runs there, but only at small sizes (0.8B fits comfortably in 18GB; 4B does not).

**Verdict for this use case:** runs well on the user's actual hardware with zero marginal cost and data staying local, but zero-shot quality for a routing-shaped, moderate-length coding-agent decision is unconfirmed-to-poor, and its one documented `noul` bug is specifically relevant to destructive-command gating. Would need fine-tuning first.

## 4. Independent benchmarks

All of the below are small, independent, non-peer-reviewed studies unless noted. Treat point estimates as indicative, not deployment thresholds. **Gap, stated outright:** I could not find an independent benchmark testing Jev's native `score` primitive on an ordinal effort-level task at scale, nor anything testing a shell-command safety judgment directly (closest: the action-gate study below, which does use native `noul`+`choice`+`score` together, just not over raw shell commands).

- **[AbdelStark/jev-benchmarks](https://github.com/AbdelStark/jev-benchmarks)**, pilot (n=300, 100/dataset), Jev vs `fastino/gliner2.5-multi-v1`: **AG News (4-way choice)**: Jev 0.910 acc vs GLiNER 0.700; coverage at ≤5% error 0.830 vs 0.240. Banking77 (72-way): Jev 0.870 vs 0.610. **DAIR Emotion (6-way; categorical labels — sadness/joy/love/anger/fear/surprise, not ordinal)**: Jev only 0.480 (not significantly different from GLiNER's 0.440) and *poorly calibrated* — Brier 0.846 vs 0.668, 16% of examples got zero probability mass on the true label. Validate per task; AG News-style numbers don't obviously transfer to affect-style categorical labels.
- **[nibzard/decision-model-benchmark](https://github.com/nibzard/decision-model-benchmark)** (DMB), `choice`-only throughout: expanded run (2026-09-29, full official test sets, 40,226 decisions, zero failures, **$1.71 total**): Banking77 (77-way) 79.2% acc, p50 316ms; CLINC150 (150-way+OOS) 88.6% acc, OOS precision 90.3%/recall 81.2%, p50 279ms; NLU++ (one binary Choice per intent) 48.3% micro-F1, only 4.3% fully-correct messages. Thresholds fit on validation and frozen: Banking77 @0.96 → 51.2% coverage at 3.68% error (under target); **CLINC150 @0.62 → 88.3% coverage but 6.65% error — missed its own 5% target on held-out test data**; NLU++ had no qualifying threshold at all. Sep-26 pilot (256 items, 6 LLMs + Jev, $10 cap): Jev matched GPT-6 Luna's banking accuracy (80.5%) and beat it on spam (98% vs 90%) at the fastest median latency (0.26–0.28s vs 0.74–3.1s); rejected 12/256 items over its ~255-option cap; mean confidence on "no good option" items 53.7%, with the authors' explicit caveat: **"Jev's native confidence remains a provider-defined score, not a calibrated probability of correctness."** Historical data: Jev p50 264–276ms (faster than every tested LLM); answer-order instability 13% pooled for Jev vs 37% for a small LLM under reordering.
- **[jujumilk3/jev-calibration-audit](https://github.com/jujumilk3/jev-calibration-audit)** (secondary-sourced — cited via the awesome-list summary, not fetched directly): on 300 ambiguous KoBBQ items, Jev chose "unknown" 95% of the time when offered that option; with it removed, forced-choice accuracy was necessarily 0%, and 79% of forced answers matched the dataset's known stereotype. **Always include an explicit "none of the above / needs review" option in a routing or destructive-command schema.**
- **[nikkoxgonzales/jev-certify](https://github.com/nikkoxgonzales/jev-certify)**, `results/REPORT.md` fetched directly — model under test is `typesafe/jev-1.13` **via the OpenRouter Decisions API, not TypeSafe directly.** CLINC150, 150 intents, 460 calibration / 400 held-out eval queries. At a 5%-per-query target: threshold 0.831, certified loss/query ≤0.0499; measured: 84.75% auto-routed, **loss/query 0.0225 (2.65% error among the routed subset — two different quantities, both real)**, certificate held. A separate scope guardrail (`noul` ≥0.671, the study's one native-`noul` calibration measurement: **Brier 0.0836, ECE 0.169**, vs ECE 0.099 for the routing confidence) certifies ≤0.65% false-accepts/query, but the looser 2%/5%/10% targets all **missed by roughly 3.3×–4×** once out-of-scope traffic prevalence shifted from 13% (calibration) to 43% (eval) — the certificate is prevalence-sensitive, not wrong; re-calibrate on traffic that matches production, or certify the conditional rate and multiply by a separately-monitored prevalence. A 1% target was infeasible at this sample size regardless: 234 of 460 calibration items return a top probability of exactly 1.0, and some of those are wrong, which floors the achievable certified rate independent of threshold choice. Cost: $0.1455/1,000 decisions, p50 0.37s, p95 0.744s, via OpenRouter.
- **[ghubnab99/jev-enterprise-decision-fabric](https://github.com/ghubnab99/jev-enterprise-decision-fabric)**, `docs/evaluations/agent-action-gate-v1.md` fetched directly — **the single most relevant study to "destructive-command checks" found.** 111 tool-call cases (labels: `Allow`/`Deny`/`RequireApproval`) across 15 failure-mode families, comparing `jev-1.13.0` direct API vs `claude-opus-5` (low effort, structured output). The gate is a three-layer design worth copying directly: **(1)** the model answers three typed contract questions — `action_requested_by_user` (native `noul`, a probability), `action_impact` (native `choice` with confidence), `scope_expansion` (native `score`, 0–2) — **(2)** a deterministic policy (`ProposedActionGate`) maps those answers plus a linguistic-risk scan to a disposition via fixed rules (e.g., request-probability ≤0.25 → `Deny`), **(3)** the disposition is compared to the label. **Per-case accuracy: Claude 102/111 (91.9%) vs Jev 100/111 (90.1%)**, disagreeing on only 10 of 111 cases (McNemar p≈0.75 — not significant at this n). **Each model produced exactly one unsafe `Allow` and one over-cautious over-block.** Jev was ~6.5× faster (p50 376ms vs 2,479ms) and ~323× cheaper by list price ($0.0000268 vs $0.008648/decision — part of that gap is Jev using under half the input tokens per call for the same contract, so it's partly price and partly prompt size, not pure rate). **Contract/policy mapping was a large error source for both, though for Jev it's tied, not dominant**: Jev had 5 classification errors, 5 contract/policy-mapping errors, 1 contract gap (11 wrong cases total); Claude had 1 pure classification error, 1 classification-plus-gate-gap error, and 7 contract/policy-mapping errors (9 wrong cases total). **The two unsafe allows are two different gaps, both outside the model — not one shared root cause.** Jev's unsafe allow (`irr-req-revoke-access`, "revoke a contractor's production IAM access," labeled `RequireApproval`): both models actually classified this one the same way, `reversible_change` at high confidence (Jev 0.93, Claude 0.72) — but Claude's 0.72 fell under the policy's 0.80 confidence floor and got escalated, while Jev's 0.93 cleared it and auto-allowed. The report's own diagnosis: the contract has no category for "reversible in principle, high-consequence in practice," and no deterministic rule exists for identity/access tool families — Claude was saved by a threshold accident, not a better judgment. Claude's separate unsafe allow (`hedge-if-overdue-then-remind`) had a different origin entirely: *"Classification + gate gap: the detector has no conditional signal"* — the deterministic risk-scanner simply has no way to detect hedged/conditional authority language at all. **Two lessons, both about the deterministic layer, not the model**: (1) hard-code always-escalate for named high-consequence tool families (IAM, force-push, prod deploy, secret/credential operations) regardless of model confidence, since a confidence floor alone can be cleared by chance; (2) add an explicit hedged/conditional-authority detector to the policy layer, since neither model's own uncertainty signal substitutes for one. Separately, nine cases where Jev selected the correct `irreversible_change` category still returned confidence 0.38–0.79 (below the dataset's own 0.80 minimum) — the correct final disposition there came from the policy's deny boundary catching it anyway, not from Jev's confidence clearing a bar, a further argument against gating solely on a single model confidence threshold.
- **[fstandhartinger/jevbench](https://github.com/fstandhartinger/jevbench)** ("Benchmark Heaven" / benchmarkheaven.com — **explicitly not TypeSafe-affiliated**, 95 systems listed, **91 ranked** as of the current v1.4.2.2 revision, fetched directly): Jev 1.13.0 ranks **#4 (63.29)**, behind three smaller specialized decision models (Imajev-4B 67.37, Plumb-4B 65.84, decider-4b-v2 64.13); under the earlier, now-superseded v1.2 scoring method it ranked **#1 (74.4)** — these two numbers are not comparable across method revisions. Pulled from the same v1.2 table so the comparison is valid: Jev 1.13.0 74.4 (#1, Intelligence 85.7) vs `kev` 0.6B research-preview 62.5 (#19, Intelligence 51.9) vs `kev` 0.5B 33.2 (#38, Intelligence 38.2) — all three served through their own production/native endpoints, a real same-method gap in Jev's favor, and a large gap between two adjacent small Kev sizes. Note: the Apple-Silicon test in §3 ran **`kev-0.8b`** specifically, a size JevBench never benchmarked (its rows are 0.5B/0.6B/4B/8B) — so neither JevBench number above can be cited as the quality of the exact checkpoint confirmed to run on an 18GB Mac. Per the v1.4.2.1 release notes, the current-method composite gap against the leading small model is explained directly: *"Jev 1.13.0 out-reasons decider-4b v2 (Intelligence 53.1 vs 49.4) and is better calibrated; decider-4b v2 leads on speed and cost"* — i.e., Jev wins on the axes most relevant to decision quality, loses on the axes most relevant to a self-hosted deployment. The composite is a broad decision-quality leaderboard (math, coding, rules & law, finance, support, safety topics), not routing-shaped-task-specific, so no separate 3–6-option-choice number could be extracted. The `laya` 421M row and its state-budget caveat are covered in §3 above. One general finding worth carrying over: the benchmark's own "open-alternative-jev" entry scored 72% with its options listed one way and **21% with the same two options reversed** — stark, independently-measured confirmation of the option-order-sensitivity problem (on a different small model, not Jev itself).

## 5. Comparison table and recommendation

| | Jev (TypeSafe) | AnyJev (self-host) | Laya (self-host) |
|---|---|---|---|
| Cost | $0.042/Mtok input, output free (verbatim docs, 2026-10-01) | Your GPU (CUDA required for the useful L2 path) | $0 marginal; your CPU/GPU |
| Latency (1 decision) | ~250–380ms p50 across most independent benches (DMB, action-gate); one benchmark (JevBench, production API, their own network path) measured 650ms p50 | 42.8ms batched / 54.6ms single, transformers+H100; 61.8ms single, vLLM+H100 (vendor bench — no Apple Silicon/CPU numbers exist) | ~33ms (T4); ~1.7s for a 4k-token doc on Apple GPU; runs on an M3 Pro per independent third-party test |
| State budget | 32k tokens (+32k for longest question, 64k total) | Whatever host LLM supports | 512–1,024 tokens (8,192 w/ degradation, multilingual only) — independently confirmed to cost accuracy on long items (JevBench footnote) |
| Option cardinality | Up to 255 (DMB: rejects 256+) | 26 (letter readout cap) | Degrades sharply >20 at defaults |
| Zero-shot quality (routing-shaped) | Strong on simple label spaces (AG News 0.91 acc); weaker/miscalibrated on categorical affect labels (Emotion 0.48); only independent native-`noul`+`choice`+`score` destructive-action study found Jev statistically tied with Claude Opus 5 | Needs 100–300 labels/question (L2) to be competitive; L0 alone mediocre (0.49–0.65) | **Near-chance on its own typed-decisions bench** (0.362 vs 0.461 majority); mid-pack (54.4) on JevBench's broader, shorter-item suite; documented `noul` label-following bug |
| Calibration story | Independent benches call confidence "provider-defined, not a correctness probability"; probabilities cluster at round numbers (56% exactly 1.0 in one study) | L0 debias (no labels) → L1 temperature (100–500 labels), doesn't survive distribution shift | Ships over-confident; must temperature-fit on your own data first |
| Hosting | Closed API only | Self-host, Apache-2.0 | Self-host, Apache-2.0 open weights |
| Apple Silicon / Fedora x86-64 | N/A (API) | **Unverified/unsupported** — CUDA-only published path, no ARM/Metal mentions anywhere in the repo | **Independently confirmed working on an M3 Pro** (community MLX port); Fedora via CPU or GPU |
| Data boundary | Leaves the machine; no-training commitment + DPA (retention tied to "necessity," not a fixed period; no SLA in the DPA); ZDR available to enterprise | Stays local | Stays local |
| Jev-API-compatible server | — (is the API) | **Not shipped** (roadmap, unchecked) | Adopts the same 3-primitive JSON shape natively |

**Recommendation:** default the personal decision layer to **Jev**, pinned to `jev-1.13.0`. It's the only option with usable zero-shot quality today at near-zero personal-use cost with no infrastructure to run, and the one independent study closest to "destructive-command checks" found it statistically indistinguishable from Claude Opus 5 on that exact task shape (100/111 vs 102/111 per-case) while an order of magnitude faster and cheaper — with the important caveat that *both* models' single unsafe-allow traced to a missing policy category, not a model failure. Build the circuit breaker on the now-confirmed SDK behavior (§1): `429` → hold exactly `retry_after_ms`/`Retry-After` when calling TypeSafe directly; `529` or any `5xx` → open circuit, exponential backoff; `401`/`422` → don't retry, fix the request; `402` or anything else outside that set → stop and alert, since no first-party code path treats it as transient. Mirror the action-gate study's architecture directly: ask Jev typed `noul`/`choice`/`score` questions about the proposed action, keep the Allow/Deny/RequireApproval mapping as deterministic code, and **hard-code an always-escalate rule for named high-consequence tool families** (IAM, force-push, prod deploy, secret/credential operations) rather than trusting any model's classification or confidence for those specifically. Always include an explicit "needs review / none of the above" option in routing schemas generally.

**Surfaced but not evaluated (worth a look later, not a recommendation today):**
- [Kev](https://github.com/jaredpalmer/kev) — small, self-hostable decision models with a **native Jev/TypeSafe-compatible `/v1/systemone` endpoint** (the realistic "self-hosted, swap-the-endpoint" path, not waiting on AnyJev's unshipped server). `kev-0.8b` runs comfortably on an 18GB Apple Silicon machine per independent third-party testing (§3); `kev-4b` does not fit in the same 18GB. JevBench scored *other* Kev sizes at 62.5 (0.6B research preview, #19) and 33.2 (0.5B, #38) against Jev's 74.4 (#1) under the same v1.2 method — real gaps, and a reminder that Kev's quality varies a lot by size/checkpoint; the specific 0.8B size confirmed to fit on a personal Mac was never run through JevBench.
- [AnyDecisionModel](https://github.com/mattt/AnyDecisionModel) — Swift package offering the same typed interface over either the Jev API or a local MLX model on Apple Silicon; calibration is caller-configured, not established.
- [laya-apple](https://github.com/tc3oliver/laya-apple) / `laya-mlx` — community MLX/ANE runtime for Laya; the one independently-tested Apple Silicon path in this research.
- TypeSafe's own [System One Adapter](https://github.com/typesafe-ai/system-one-adapter-python) — runs the same typed Choice/Score/Noul interface over OpenAI, Anthropic, or OpenAI-compatible APIs; a reasonable circuit-breaker fallback path when Jev's circuit is open, since it needs no new integration code once Jev's primitives are already in use.

**Reconsideration triggers:**
- AnyJev ships both the Jev-compatible HTTP server *and* a non-CUDA backend (MLX/llama.cpp/CPU) → re-evaluate self-hosting on the Mac.
- A self-hostable, Jev-compatible-endpoint model (Kev or a future one) closes the JevBench Intelligence gap *at the specific size that fits on Apple Silicon* (today: `kev-0.8b` fits an 18GB Mac but was never run through JevBench; the sizes JevBench did run, 0.5B/0.6B, both trail Jev by a wide margin) → re-evaluate self-hosting generally, since the endpoint-compatibility problem flagged for AnyJev doesn't apply to Kev.
- Laya ships a zero-shot checkpoint competitive on a routing-shaped, moderate-length task, fixes the `noul` label-following bug, or you're willing to fine-tune on your own routing/command history → re-evaluate for the zero-marginal-cost, data-never-leaves-the-machine option, especially for destructive-command gating.
- TypeSafe's status-page incident rate rises materially above ~99.8%, or someone confirms how (or whether) credit exhaustion actually presents on the direct API → revisit the "unknown status → stop and alert" default.
- A workplace vendor/legal review of the actual DPA (now located and read, §1) comes back negative for the `easygo` context specifically, e.g. over the lack of a fixed retention ceiling or SLA → fall back to self-hosted Laya/Kev/AnyJev there despite the accuracy gap.
